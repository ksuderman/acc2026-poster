Galaxy on AnVIL

Galaxy brings an accessible, reproducible analysis environment to AnVIL's secure cloud ecosystem. Through a familiar web interface researchers run established bioinformatics tools, build reusable workflows, track complete histories and share methods and results — without managing command-line software or cloud infrastructure.

The deployment keeps Galaxy's core services on a small, cost-conscious virtual machine and sends computationally intensive jobs to Google Cloud Batch, which provisions right-sized resources on demand and releases them when the work is done.

We report on three fronts: a rebuilt deployment that is far easier for both the Terra and Galaxy teams to maintain, elastic compute that decouples cost from wall-clock time, and early work bringing AI co-scientists to AnVIL.

Maintenance, Simplified

The deployment was rebuilt around one principle: each team should only have to change the thing it owns.

For the Terra team

  • No custom VM image to rebuild. Terra supplies instance metadata; the playbook is fetched from Git at boot.
  • No code change to move Galaxy versions. The release is a Helm chart version inside the playbook, not something baked into an image.
  • Nothing hardcoded per workspace. Project, region, network, subnet, NFS export path and external IP are discovered at runtime from the metadata server.
  • Detection lives in the role, not the launcher — so it works regardless of how the VM was bootstrapped.

For the Galaxy team

  • Releases propagate themselves. A galaxy-helm release fires a repository dispatch that opens a pull request against the playbook, chart version bumped and testing checklist attached.
  • One source of truth for versions, replacing scattered command-line overrides.
  • Mixins instead of forks. Two dozen composable Helm value files deep-merge in order, and playbook-computed settings merge under user choices rather than clobbering them.
  • Continuous testing launches a real GCE instance on every pull request.
The golden Batch VM image is published once in a shared project and readable by all authenticated users, so a workspace in any project can boot Batch workers from it — the image it runs is independent of the project the job runs in.

Elastic Compute with Google Cloud Batch

Job routing is driven by Total Perspective Vortex (TPV). Small, latency-sensitive work stays on the node; anything larger falls through to Batch.

1
TPV inspects the tool and its declared resource needs
↓
2
Jobs within 1 core / 4 GB run locally on the VM
↓
3
Everything else goes to Google Cloud Batch, which provisions a right-sized VM
↓
4
The worker mounts NFS and CVMFS, runs the tool container, and is released

Per-tool sizing is declarative, so demanding tools get real hardware without provisioning it in advance:

MetaPhlAn — 16 cores / 96 GB FastQC — 16 cores / 64 GB fastp — 8 cores / 32 GB

Right-sizing is literal. The runner maps requested cores and memory onto a machine shape by memory-per-core ratio — high-CPU, standard or high-memory — and picks the smallest size from 2 to 128 vCPUs that fits. Limits reject oversized jobs rather than silently shrinking them, so multi-core work really does leave the node.

Reference data comes along. Batch workers boot from the same CVMFS-preconfigured image as the Galaxy VM and bind-mount the Galaxy reference data repositories read-only.

Every Batch job carries its Galaxy job ID, so work can be followed from the Galaxy UI straight into the Cloud Console. Improvements to the Batch runner developed for AnVIL are contributed upstream to Galaxy rather than carried as local patches.

Cost: Paying for Work, Not Uptime

A managed Kubernetes cluster bills continuously for a control plane and a node pool sized for the biggest job it might ever see. A small VM plus Batch bills a modest fixed rate and adds cost only when analyses run.

Projected cumulative cost over one week of continuous availability. The managed-cluster line climbs whether or not anyone is analyzing data; VM + Batch steps up per job.

~$57

  • Idle is cheap. A Galaxy that is up but unused costs one small VM.
  • Headroom is free. Nothing is provisioned in advance for the largest anticipated job.
  • Effectively unlimited scale. Concurrency is bounded by cloud quota, not a fixed node pool, and each job maps to the resources it consumed.

AI Co-Scientists: GalaxyAI, Orbit, and Where the Model Runs

One front door, two destinations. Prompts leave Galaxy for a single in-cluster endpoint, which routes them either to a GPU running inside the trust boundary or out to an assured hosted model — a configuration change, not a redeployment.

GalaxyAI is a multi-agent system inside Galaxy: a router hands each question to a specialist — error analysis, tool recommendation, history, training — and every answer is labelled with the agent that produced it.

Agents reach Galaxy through its Model Context Protocol server, which exposes histories, datasets, tools, jobs and workflows as 44 typed operations routed through Galaxy's own service layer, so an agent inherits exactly the authorization a user has. Orbit, running the Loom agent, provides the chat interface — on AnVIL it is packaged as a Galaxy Interactive Tool, launched from the tool panel and running inside the user's own instance.

The open question: where does the model run?

Self-hosted
  • Runs inside the trust boundary; prompts never leave
  • Open weights, no per-token charge — but a GPU billed by the hour, busy or idle
Hosted (Gemini for Government)
  • Stronger reasoning and tool use, nothing to keep warm
  • Per-token pricing, and prompts egress from the boundary
Broader rollout is pending NIH policy guidance on using large language models with controlled-access data. Resolving the policy question, not the engineering, is what determines how GalaxyAI reaches the AnVIL community.
